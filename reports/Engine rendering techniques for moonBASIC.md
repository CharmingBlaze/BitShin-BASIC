# Fix the frame, then paint the landscape

Real engines stay smooth across old and new hardware by bundling settings per bottleneck, holding a GPU budget with a feedback controller, falling back explicitly, and above all by not rendering things twice; none of the techniques moonBASIC needs for this requires leaving OpenGL 3.3 fragment shaders. moonBASIC's GL 3.3 path already has more than Godot's equivalent renderer, so its next gains are mostly corrections rather than features: a whole-scene refraction redraw, an 8x window G3N forces and nothing uses, an anti-aliasing pass that is really a blur running in the wrong place, water colour from a smoothstep, and fog that never reads the sky. The target look maps to a short list. Long soft shadows need caster reach and proxies. Real foliage needs a lighting fix before a mesh fix. Natural cliffs start by removing a sine wave and a non-tiling texture. Turquoise water is one exponential. Blue mountains come from sharing one atmosphere between sky and surfaces. The order below starts with per-pass measurement on a second GPU, because moonBASIC has only ever been measured on a Radeon 780M, then takes the near-free corrections, then the bakes and generators, and leaves render graphs, deferred shading, new backends, virtual texturing and occlusion culling unbuilt. Against the added benchmark, OGRE 1.x, moonBASIC already ships far more outdoor content and game systems but lets developers change much less of the pipeline, so "as powerful as OGRE" adds about eight small-to-medium items, led by anisotropic filtering, user render targets with a custom post chain, and a disk shader cache. Embedding OGRE itself is not worth it. The ranking itself is judgement: I found no benchmark comparing these techniques on one machine, and no Intel HD or Mac numbers exist for moonBASIC at all.

## Five kinds of evidence, and only one GPU behind the measured kind

Every claim below carries one of five labels. **Measured** means moonBASIC numbers recorded in its own docs or comments. **Code** means I or a researcher read it in the repository or in G3N v0.2.0; it says what the code does, not what it costs. **Published** means someone else's number on someone else's hardware, often old, and it transfers only as a shape. **Estimate** means arithmetic or a cost guess made for this report. **Hypothesis** means an untested prediction with a named test. Repository line numbers reflect the current uncommitted working tree.

The measured set is small and comes from a shared machine whose timings "moved a lot from run to run" (`docs/GRAPHICS.md:90`). The roadmap states the limit directly: hardware compatibility is "measured on a Radeon 780M only" (`docs/ROADMAP.md:110`), and the reference images were never compared on another GPU (`docs/GRAPHICS.md:170`).

| Measured on Radeon 780M | Result | Source |
|---|---|---|
| Drawing straight to G3N's 8x window versus the post pass | About 3x slower, with a stall of seconds on the switch | `internal/runtime/quality.go:39-41` |
| Scene MSAA on the island | 2x about 1.8 ms (10% of frames past 16.7 ms), 4x about 4 ms | `quality.go:34` |
| 5,000 cubes, batching off then on | 58.7 ms and 5,000 draws, then 6.6 ms and 1 draw | `docs/GRAPHICS.md:84` |
| City of 3,600 meshes, 28,800 copies | 43.7 ms and 3,602 draws, then 36.7 ms and 218 draws | `docs/GRAPHICS.md:86` |
| `island_orbit` camera path, dynamic resolution off | 16.5 ms frame, 6.3 ms render CPU, "the GPU sets the frame time" | `docs/GRAPHICS.md:88` |
| Cutting the city's far plane to 120 units | Not faster, so occlusion culling "would not help these scenes" | `docs/GRAPHICS.md:90` |

Two caveats matter. The 16.5 ms figure sits suspiciously close to the 16.67 ms vsync interval, so it could be vsync wait rather than GPU cost (hypothesis; per-pass timers settle it). The research brief also cited about 1.9M triangles and a 2-second first-frame stall. I did not find either in the docs or runtime comments I searched, so treat both as unverified until re-measured.

## Shipping engines bundle settings, budget frames, and fall back explicitly

No engine read here scales one renderer smoothly from old to new. **Godot ships three renderers**, and its OpenGL 3.3 path, Compatibility, is deliberately reduced: non-clustered forward, one pass for unshadowed lights and extra passes for shadowed ones, tonemapped sRGB output with no HDR, no compute, and only bilinear 3D scaling with no FSR ([renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html), [architecture](https://docs.godotengine.org/en/stable/engine_details/architecture/internal_rendering_architecture.html), [scaling](https://docs.godotengine.org/en/stable/tutorials/3d/resolution_scaling.html)). Its docs give the cost model moonBASIC should expect: low base cost and high scaling cost, with Forward+ the slowest on old hardware. Godot's docs disagree with each other on the Compatibility colour buffer (R10G10B10A2 versus RGBA8), so do not cite either without checking source. The practical conclusion stands: with FSR 1, an HDR target, GTAO and a post chain, **moonBASIC's GL 3.3 path already exceeds Godot's equivalent**, so parity with Godot's compute features is the wrong goal. Godot's sRGB and linear mismatch between shadowed and unshadowed lights is also a warning. moonBASIC's Low tier stays on the old gamma path (`docs/GRAPHICS.md:164`), so Low and Medium look different by construction, and the same document says every tier now keeps the post pass that linear lighting needs. Test whether Low can move to linear (hypothesis: the added cost is small).

**Unity and Unreal separate quality bundles from the runtime controller.** Unreal maps `sg.*` groups at levels 0-3 onto cvars in an ini file, with device profiles on top ([scalability](https://dev.epicgames.com/documentation/unreal-engine/scalability-reference-for-unreal-engine?lang=en-US)). Unity bundles settings per quality level in URP Assets, and its SRP Batcher reduces state changes rather than draw count, using persistent per-material data and one per-object buffer ([SRP Batcher](https://docs.unity.com/en-us/engine/current/manual/analysis/graphics-performance-profiling/in-urp/reduce-draw-calls-urp/srpbatcher/srpbatcher)). Both limit dynamic resolution to APIs they trust for timing, and neither lists OpenGL ([Unity](https://docs.unity3d.com/2022.3/Documentation/Manual/DynamicResolution.html), [Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/dynamic-resolution-in-unreal-engine)). Epic names wrong GPU timings as the risk, so moonBASIC must sanity-check GL timer data, which its controller partly does by falling back to frame time when no GPU timer exists (`dynres.go:142`).

**Source and id Tech show two ends of the same arc.** Source picked a feature level from a GPU table in `dxsupport.cfg`, then moved to shader and effect options plus GPU memory detection from the Left 4 Dead branch on ([VDC](https://developer.valvesoftware.com/wiki/Dxlevel); search extracts only, the wiki blocked direct fetches). id's public numbers come mostly from one third-party capture of Doom 2016 on a GTX 980: clustered forward with 3,072 clusters built on the CPU, a depth pre-pass with `EQUAL`, half-resolution SSAO, quarter-resolution bloom, an 8k shadow atlas with most maps reused from the previous frame, and 1,331 draw calls ([Courrèges](http://www.adriancourreges.com/blog/2016/09/09/doom-2016-graphics-study)). The copyable parts are shadow reuse and half or quarter-resolution effects, not virtual texturing. moonBASIC's 218-draw city is already well under that draw count, which suggests draw count is no longer its main problem (hypothesis).

**Croteam's value is structural, and its evidence is uneven.** I found no public Serious Engine 2 source; the official release covers SE1 v1.10 only, so nothing in that repository can be attributed to Serious Sam 2 ([README](https://github.com/Croteam-official/Serious-Engine/blob/b408e88a16fd01aa1cfd0e0a999c86c2c1437c9e/README.md)). The one deep SS2 source, iXBT's 2006 analysis, is outside observation. It reports an FP16 HDR path with LDR fallback, a single unfiltered sun shadow map capped at 512x512 with everything else baked, terrain collapsing from 1 pass in ps_2_0 to 3 in ps_1_1, and a fillrate-test "Auto detect quality" ([iXBT](https://www.ixbt.com/video2/tech_ss2.shtml)). Its measured costs on a GeForce 7800 GTX-class system are the only per-setting numbers in this research: **dynamic shadows cost up to 35% at max settings and geometry LOD 30-35%**, while HDR cost under 10% and anisotropy, bloom, filtering and particles 2-4% each. Those are 2006 proportions on a fast card, so read them as a hypothesis to retest: shadows and LOD first, post second.

The SE1 code shows no frame-time-driven quality at runtime in what was searched. It applies per-GPU scripts by renderer pattern at startup, and an unknown GPU prints "Automatic adjustment disabled" ([GLSettings.cpp](https://github.com/Croteam-official/Serious-Engine/blob/b408e88a16fd01aa1cfd0e0a999c86c2c1437c9e/Sources/SeriousSam/GLSettings.cpp#L121-L135)). It runs logic at 20 Hz with interpolated rendering ([Timer.cpp](https://github.com/Croteam-official/Serious-Engine/blob/b408e88a16fd01aa1cfd0e0a999c86c2c1437c9e/Sources/Engine/Base/Timer.cpp#L54)), uses global LOD multipliers per system ([RenderModel.cpp](https://github.com/Croteam-official/Serious-Engine/blob/b408e88a16fd01aa1cfd0e0a999c86c2c1437c9e/Sources/Engine/Models/RenderModel.cpp#L505-L520)), and draws lowest-LOD terrain tiles together with one baked top map ([TerrainRender.cpp](https://github.com/Croteam-official/Serious-Engine/blob/b408e88a16fd01aa1cfd0e0a999c86c2c1437c9e/Sources/Engine/Terrain/TerrainRender.cpp#L995-L1007)). The famous Legion System has no public method. Croteam's own words are "trick" ([GINX](https://www.ginx.tv/en/serious-sam-4-release-window-legion-system)), so do not cite it as instancing, impostors or anything else specific.

These engines combine into one startup design. moonBASIC already has half of it, and its `autoTier` shows the limits of name matching (Code, `quality.go:62-74`). Any "UHD Graphics" string contains "hd graphics", so a recent UHD 770 lands with the HD 520 on Low, while every unknown discrete card, however old, starts on High and can only be corrected downward. The fix is a capability check, then a small denylist, then a sub-second timed scene on first launch or GPU change, stored per renderer string, then dynamic resolution. SS2's fillrate test and Unreal's `SynthBenchmark` scoring are the precedents ([Looman](https://tomlooman.com/unreal-engine-optimal-graphics-settings/), community source). Benchmark thresholds need calibrating on real machines; research cannot supply them. Unreal's ini structure also fits: express tiers as data with separate shadow, post, texture and effects groups, and borrow Talos's grouping of options by CPU, GPU and memory bottleneck ([Steam guide](https://steamcommunity.com/app/257510/discussions/0/364040961449374759), community source).

## Smoothness is lost in five known places

**The first is the window.** G3N hardcodes `glfw.WindowHint(glfw.Samples, 8)` between `glfw.Init` and `CreateWindow` with no hook (Code, verified at `window/glfw.go:243`), and upstream master still does ([master](https://raw.githubusercontent.com/g3n/engine/master/window/glfw.go)). moonBASIC already renders through its own targets, so those samples add nothing. At 1080p they represent about 66 MB of colour plus 66 MB of depth-stencil before compression (estimate; the driver may grant a different count). There is also a possible silent bug: `blitSceneCopy` blits to a differently sized rectangle at HiDPI (`postfx.go:440-443`), and GL returns `INVALID_OPERATION` if either buffer is multisampled and sizes differ ([glBlitFramebuffer](https://registry.khronos.org/OpenGL-Refpages/gl4/html/glBlitFramebuffer.xhtml)), with error checks off in moonBASIC (hypothesis; test on a scaled display). The fix needs a patched G3N, since nothing outside `window.Init` can change it.

**The second is the controller.** Published controllers measure GPU time, drop fast and raise slowly. Valve's numbers for a 90 Hz frame keep utilization between 70% and 90%: over 90% in the last frame drops 2 levels and waits 2 frames, three frames under 70% raises 1, and over 85% with a linear prediction past 90% also drops ([Valve](https://cdn.fastly.steamstatic.com/apps/steamdevdays/slides2016/ScalingGreatVR.pdf)). Unreal adds history, minimum change size, change period, headroom, and a panic path that resets history after consecutive over-budget frames ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/dynamic-resolution-in-unreal-engine)). moonBASIC's controller differs in kind (Code, `dynres.go:20-124`): it judges half-second windows, counts a frame late only past 115% of budget, drops when over a quarter are late, and uses GPU time only to decide whether a frame was "busy". At 60 Hz, that means frames up to 19.2 ms count as on time, and under vsync a problem appears only after vblanks have already been missed. My prediction is that it reacts after visible stutter (hypothesis). Scaling Valve's rules to 60 Hz gives 15.0 ms, 14.2 ms and 11.7 ms thresholds (estimate). Keep the existing floors, read a ring of 3-4 query objects without blocking, discard samples from an older scale, and treat a controller stuck at its floor as CPU-bound or vertex-bound. Allocate targets at maximum size and render a sub-viewport, as Unity and Unreal do; confirm whether `setScale` currently reallocates.

Add Godot's mip bias, `log2(min(scale, 1.0))` plus a small negative offset for post AA ([Godot](https://docs.godotengine.org/en/stable/tutorials/3d/resolution_scaling.html)). Godot's own Compatibility renderer lacks this, so a one-line change exceeds it. FSR 1's published upper bound is 0.2-0.5 ms at 1440p across AMD's enthusiast to mainstream GPU groups ([AMD](https://gpuopen.com/fidelityfx-superresolution/)); I found no integrated-GPU figure.

**The third is pacing, where GL 3.3 has the least to offer.** Croteam's Alen Ladavac argued that render duration misleads and that present time is the useful signal, testing `VK_GOOGLE_display_timing`, which is a Vulkan extension ([Phoronix](https://www.phoronix.com/news/GDC-Vulkan-Stutter-Frames)); his original post could not be fetched. I found no GL equivalent. What remains: stay under budget, keep vsync on, insert a fence at frame end and wait on the fence from 1-2 frames back to bound queue depth ([Khronos forum](https://community.khronos.org/t/swapbuffers-and-synchronization/107667)), and smooth the simulation delta. `glFinish` after swap is contested on the same forums, so make it an option rather than a default. Report percentiles and missed vblanks, not average FPS. Evidence here is forum-grade, which is why row 15 ranks below items with firmer support.

**The fourth is shader compilation.** Program binaries can exist on 3.3 as an extension, but `NUM_PROGRAM_BINARY_FORMATS` may legally be 0 and failure is silent, setting `LINK_STATUS` false after a driver update, so source fallback is mandatory ([ARB_get_program_binary](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_get_program_binary.txt)). `KHR_parallel_shader_compile` adds non-blocking status polling where exposed ([spec](https://registry.khronos.org/OpenGL/extensions/KHR/KHR_parallel_shader_compile.txt)). Dolphin's experience shows caching alone cannot remove first-run stutter, because GPU changes and driver updates invalidate it ([Dolphin](https://dolphin-emu.org/blog/2017/07/30/ubershaders/)). Mesa already keeps a 1 GB disk cache ([Mesa](https://docs.mesa3d.org/envvars.html)), so Linux gains less. One source says Intel's macOS drivers expose no binary formats ([Cookbook](https://www.oreilly.com/library/view/opengl-4-shading/9781789342253/bae34249-478a-44d2-b0e6-17b3ce90f067.xhtml)), so assume a recompile each launch there. The order is: log compile time per program, enumerate variants, compile behind a loading screen with polling or time-slicing, warm with a small draw, then cache binaries keyed on source hash plus vendor, renderer and version strings. There is a specific trap in G3N: light counts feed `ShaderSpecs` ([shaman.go](https://github.com/g3n/engine/blob/v0.2.0/renderer/shaman.go)), so a script spawning a light at runtime should force a new program (hypothesis from code reading). Fixed light slots with a count uniform remove it, matching Godot's per-mesh limit of 8.

**The fifth, and largest, is redraws.** With the default 4 cascades (`docs/SHADOWS.md:9`), plus reflection, refraction and main, a water scene has 7 views. If the brief's 1.9M triangles is right, that is an upper bound of 13.3M triangles per frame before culling (estimate). Dynamic resolution cannot help that vertex work. The most effective order is: per-cascade culling, far-cascade caching, water pass removal (see the water section), shadow LOD, then occlusion only if measurements ask for it. moonBASIC already picks simpler LODs for directional shadow tiles on batched meshes (`docs/GRAPHICS.md:74`). Published support is qualitative: Cyberpunk 2077 uses a budgeted, multi-frame distant shadow map, interval-based cascades and tight convex culling, and its offline visibility bake cut triangles "by millions" with no percentage given ([Dybisz and Witanowski](https://history.siggraph.org/wp-content/uploads/2022/06/2021-Talks-Dybisz_Shadows-Optimizations-in-Cyberpunk-2077.pdf)). I found no published millisecond saving for cascade caching. On Intel HD class hardware, expect resolution to sit at its floor, at which point the tier is what matters.

## Keep forward, own the draw list, and patch G3N thinly

**Forward is right for this look.** MSAA, transparent paths and custom shaders all favour it, and the deferred case is weak on integrated GPUs. Light scale is the only thing clustering buys. The cheap first step is what Godot Compatibility does: a fixed top-N lights per object. Clustering on GL 3.3 is feasible with CPU assignment if games ever need dozens of visible lights, on the patterns in Filament's froxel texture and 16 KiB UBOs ([Froxelizer.h](https://raw.githubusercontent.com/google/filament/main/filament/src/Froxelizer.h)) and Bevy's CPU fallback ([bevy_pbr](https://docs.rs/crate/bevy_pbr/latest/source/src/cluster/mod.rs)). Prefer integer textures over buffer textures if ANGLE is a possible future. A landscape with one sun does not need any of this yet.

**A depth pre-pass should be optional, not default, because the sources conflict.** Doom uses one with `EQUAL` ([Courrèges](http://www.adriancourreges.com/blog/2016/09/09/doom-2016-graphics-study)). Arm says the doubled draws and vertices usually outweigh the benefit on Mali, though that reasoning rests on Mali's hardware ([Arm](https://support.arm.com/documentation/101897/0304/Optimizing-application-logic/Draw-call-batching-best-practices)). Unity disables Depth Priming under MSAA and says the gain depends on overlap and shader complexity ([Unity](https://docs.unity.com/en-us/engine/current/manual/render-pipelines/universal-render-pipeline/urp-reference/urp-universal-renderer)). Intel's Gen11 guide is silent on it. MJP's test shows why alpha-tested foliage is the interesting case: `discard` with depth writes raised front-to-back invocations from about 440,640 to 582,000, and a depth-only alpha prepass with `EQUAL` avoids that ([MJP](https://therealmjp.github.io/posts/to-earlyz-or-not-to-earlyz/)). Fix the sort first, since correct front-to-back order is free. Then test a partial prepass of terrain and large occluders, and of alpha-tested foliage, on an immediate-mode integrated GPU.

**The sort is currently wrong, and that is verifiable.** `zSort` applies `ModelViewMatrix` to `Position()` (Code, verified at `renderer.go:290-295`). That matrix already contains the node's translation, so the offset is counted twice for any node away from its parent's origin. No bug report confirms the effect, so a test should. G3N also has no material or program term in its sort, allocates shader defines per draw, re-sends light uniforms per draw, and finds programs by linear scan ([renderer.go](https://github.com/g3n/engine/blob/v0.2.0/renderer/renderer.go), [shaman.go](https://github.com/g3n/engine/blob/v0.2.0/renderer/shaman.go)). `batch.go:23` records the lookup and uniforms at about 11 microseconds per object on the 780M (measured).

The practical shape is a **small vendored G3N patch** through the `replace` mechanism `go.mod` already uses, at an estimated few hundred lines: window samples, `zSort`, allocations, hashed program lookup, fixed light slots. Offer it upstream, since upstream is active ([g3n/engine](https://github.com/g3n/engine)), without depending on acceptance. Then extend the existing raw GL path into moonBASIC's own draw list for world geometry. Copy a 64-bit key: layer, translucency, then program, material and coarse depth for opaque, and depth for transparent ([Ericson](https://realtimecollisiondetection.net/blog/?p=86), [three.js](https://raw.githubusercontent.com/mrdoob/three.js/dev/src/renderers/webgl/WebGLRenderLists.js)). Add a hashed program key and named shader chunks, and run passes as plain ordered calls. Scripts only see integer handles, so this stays invisible to them, and only 11 runtime files import `renderer` against 137 touching G3N at all. Do not replace `math32`, which sits in 91 files and gains nothing. Row 28 ranks low because its payoff is unproven until a CPU profile exists, and the docs note that above 10,000 entities most CPU time is per-frame walks over material state (`docs/GRAPHICS.md:90`), which a sort key alone will not fix.

**On macOS, stay on native GL and buy insurance cheaply.** Apple deprecated GL in 10.14 and tops out at 4.1 ([Apple](https://support.apple.com/en-us/101525)); I found no removal date. ANGLE over Metal covers ES 3.0 and is Godot's path with a native fallback, added to stop crashes on older Macs ([ANGLE](https://raw.githubusercontent.com/google/angle/main/README.md), [Godot PR](https://github.com/godotengine/godot/pull/83753)). It is not drop-in here: G3N opens the OpenGL framework directly ([glapi.c](https://github.com/g3n/engine/blob/v0.2.0/gls/glapi.c)), 27 files import the v3.3-core binding, and shaders need translating. Zink on macOS is "experimental with very limited capabilities" ([Mesa](https://docs.mesa3d.org/drivers/zink.html)). KosmicKrisp needs M1 and macOS 26, and Intel Macs would need MoltenVK alongside it ([LunarG](https://www.lunarg.com/kosmickrisp-achieves-vulkan-1-4-conformance-on-apple-silicon/), [MoltenVK](https://raw.githubusercontent.com/KhronosGroup/MoltenVK/main/README.md)). So keep new shaders ES 3.0-friendly where that costs little, avoid geometry shaders and buffer textures in core paths, and test on real Macs. If a second backend ever gets funded, my rough ranking is wgpu behind a thin moonBASIC renderer, then bgfx with a self-maintained binding, then raw Vulkan. Timer queries may mislead on tile-based GPUs ([ARB_timer_query](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_timer_query.txt)), so combine them with frame pacing data on Apple Silicon.

## Natural cliffs start by deleting a sine wave

The reported hard horizontal stripes have a likely culprit that is not the normals, though nothing has been rendered to confirm it. The rock texture adds `0.07 * sin(v*52 + n2*6)` to every channel (Code, verified at `terrain_tex.go:91`). 52 is not a whole number of cycles (8.28 per tile), the noise has no wrap, and the texture repeats. Side projections map `v` directly to world Y at scale 0.055 (`terrain_shaders.go:173-175,233`). That predicts **a hard level line every 18.18 m with soft bands about 2.2 m apart inside each tile** (estimate from the code). The shader adds separate strata in 1.82 m cells (`terrain_shaders.go:236-241`), and its own comment warns about them.

| Rank | Cause | Signature | Decisive test |
|---|---|---|---|
| 1 | Non-tiling rock texture | One-texel level lines every 18.18 m | Double the scale: spacing halves. A known-tiling texture removes them |
| 2 | Sine strata in the texture | Soft 2.2 m bands, stronger in linear light | Drop the term at `terrain_tex.go:91` |
| 3 | Shader strata | Irregular 1.82 m bands, ignore texture scale | Set `strataK` to 0 |
| 4 | 8-bit height source | True contours at `hscale/255`, visible in wireframe | Log decoded image type |
| 5 | Normal epsilon below height cell | Lines along grid axes, cross contours on diagonal faces | Normals as colour; `eps = max(hfCell, normCell)` |
| 6 | Tangent degeneracy at near-±Z faces | Sharp breaks on those cliffs | Disable `TerrainHasRockN` |
| 7 | Constant triangle diagonal | Diagonal sawteeth following the mesh | Flip the diagonal |
| 8 | Shadow acne | Bands crawl with the sun | Disable the shadow term |

A fast triage: white albedo with lighting separates colour causes from normals, normals-as-colour separates height causes, and raising the terrain 5 m shows which stripes stay at world height. A user-supplied rock texture changes ranks 1 and 2.

The proper fix keeps going. Make procedural textures truly tile with an integer-period lattice. Any strata should follow `y + dip·(x·a + z·b) + warp(xz)`, with warp larger than one band, stay at ±5% or less in linear space, and be masked to steep rock (estimate of good starting values). Decorrelate projections with different offsets. Base weights on the geometry normal, tightening as GPU Gems 3 does ([ch. 1](https://developer.nvidia.com/gpugems/gpugems3/part-i-geometry/chapter-1-generating-complex-procedural-terrains-using-gpu)), and give each projection its own normal frame using Whiteout blending at about 7 ALU per plane ([Self Shadow](https://blog.selfshadow.com/publications/blending-in-detail)). Biplanar sampling saves a fetch on cheap tiers, with artefacts near (±1, ±1, ±1) normals ([Quilez](https://iquilezles.org/articles/biplanar), search summary).

**The bake delivers most of the remaining gain.** Losasso and Hoppe store an 8-bit normal map at twice geometry resolution, because per-vertex normals are too blurry ([Geometry Clipmaps](https://www.hhoppe.com/geomclipmap.pdf)). For moonBASIC that means one world-space normal texture per finite map from float heights before compaction, stored in RG8 or RG16 with Y rebuilt, with mips, plus slope, curvature, AO and erosion-flow masks replacing the screen-derivative cavity term (`terrain_shaders.go:337-340`). A macro colour map breaks repetition at all distances for one fetch.

**The current terrain shader is the largest known fragment cost.** On the non-cheap path it performs about 32 fetches per pixel and 15 or more `terrainNoise` calls before shadows (Code count, `terrain_shaders.go`). Skipping zero-weight layers should reduce this to about 6-12 for most pixels (estimate). Use `textureGrad` inside branches and in `stochasticRGB`, because random offsets in a pixel quad create large implicit derivatives, which can draw one-pixel grid lines (hypothesis). Swap to Quilez's two-fetch tiling on cheap tiers ([Quilez](https://iquilezles.org/articles/texturerepetition/), search summary), and store real height in alpha instead of luminance. The "grass lacks fine texture" complaint has an arithmetic explanation: 140 cycles over 192 texels is 1.37 texels per cycle, past Nyquist, so that octave aliases at bake time (estimate). A detail layer repeating every 1-2 m, faded by distance, addresses it cheaply.

**Better mountains come from noise structure and erosion order.** `fillMountainIsland` takes one `abs` of a 6-octave sum, so it creates one crease system; the Perlin uses only four diagonal gradients with no octave rotation (Code, `heightmap_gen.go:131-155`, `noise.go:41-52`). Per-octave ridging with weight feedback, Quilez's derivative damping and domain rotation ([Quilez](https://iquilezles.org/articles/morenoise/), search summary), and 9-11 octaves on large maps should give branching ridges (hypothesis). One comparison finds fBm, warp and ridge noise all plausible but unlike real terrain because they lack erosion; its simulation route is roughly O(N³) and its river-network route O(N² log N) ([terrain-erosion-3-ways](https://github.com/dandrino/terrain-erosion-3-ways)). Thermal and droplet functions already exist (`heightmap_gen.go:425,499`). So run staged droplets at 512, 1024 and 2048, then a thermal pass, pit fill, and D8 flow accumulation ([Cinevva](https://app.cinevva.com/blog/2026-05-13-open-world-browser-part-27-island-and-terrain), secondary), and export the masks. D8 gives gameplay rivers and splat inputs for little code. FastNoise Lite's single-file Go port is MIT and covers OpenSimplex2, cellular and domain warp ([FastNoiseLite](https://github.com/Auburn/FastNoiseLite)); keep existing noise where seed stability matters, since swapping the base changes every seed.

**Leave geometry LOD alone for now.** Seams are not the reported problem. If terrain LOD is ever rewritten, CDLOD suits mountains best: per-vertex morphing, no stitching strips, 3D distance, SM3-class requirements ([CDLOD paper](https://raw.githubusercontent.com/fstrugar/CDLOD/master/cdlod_paper_latest.pdf), the author's own comparison). Clipmaps follow 2D position and need trim strips, but suit huge streaming maps ([GPU Gems 2](https://developer.nvidia.com/gpugems/gpugems2/part-i-geometric-complexity/chapter-2-terrain-rendering-using-gpu-based-geometry)). No source benchmarks them on the same hardware.

## Real foliage is a lighting fix before it is a mesh fix

Crysis shaded thousands of plants with Lambert, a translucency term, hemisphere ambient and baked AO, so production foliage models can be simple ([GPU Gems 3 ch. 16](https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-16-vegetation-procedural-animation-and-shading-crysis)). The near-black canopy likely comes from, in checking order: screen-space AO multiplying sun or translucency, a neutral ambient, canopy self-shadowing, and the tone mapper's toe. That toe is real arithmetic: the Narkowicz fit maps 0.01 to 0.0038, or about 25/255 down to about 12/255 in display terms. A vegetation green near 0.22 linear with ambient 0.3 and AO 0.4 lands near 35/255 (estimate from Filament's sRGB vegetation value and assumed lighting). Multi-bounce AO alone will not rescue it, since at v = 0.3 and albedo 0.2 it returns only about 0.35 (estimate using the [Jimenez fit](https://www.iryoku.com/downloads/Practical-Realtime-Strategies-for-Accurate-Indirect-Occlusion.pdf)).

The recommended term is a hemisphere ambient near 2:1 up to down (Crysis's ratio), blue-tinted from above and warm green from below, multiplied by `max(canopyAO * mix(1.0, screenAO, 0.35), aoFloor)`, plus normalized wrap ([Filament](https://google.github.io/filament/Filament.md.html)) and Crysis's back translucency sampled with a softened shadow. The 0.35 floor and blend are guesses to tune, and no authoritative source exists for them. Do not raise flat ambient, which is what flattens forms. Blender and the Jimenez form disagree on coloured multi-bounce, with Blender using luminance because coloured "looks bad" ([Blender](https://developer.blender.org/rB779c950098e46a34f89f1705be61b4b24be11568)), so start with luminance on foliage.

**Canopy normals do the most for shape.** Point them outward from a central sphere or cone, which hides that the mesh is cards or clumps ([NedMakesGames](https://nedmakesgames.medium.com/creating-a-foliage-shader-in-unity-urp-shader-graph-5854bf8dc4c2)), and do not flip back faces when using them ([ez-tree](https://raw.githubusercontent.com/dgreenheck/ez-tree/main/src/lib/tree.js)). For solid low-poly canopies, blend face and sphere normals near 0.6 (starting value), so facets read softly while the crown lights as one volume.

**Variation must go through instance attributes, or batching breaks.** moonBASIC's batcher splits any material difference into a new group and draws swaying trees alone, while cut-out casters draw one by one into the shadow map (Code, `docs/GRAPHICS.md:70-72`). So colour variation and wind should be one vec4 instance attribute plus vertex channels: R wind weight, G clump phase, B height gradient, A baked AO (design). Crysis's bending keeps length by renormalizing, and its detail waves use cheap smoothed triangle waves ([GPU Gems 3](https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-16-vegetation-procedural-animation-and-shading-crysis)). Add world-XZ patch noise so colour drifts across a hillside rather than looking like static. Keep shifts small, about ±5% value (starting value).

**Trees need no art assets.** ez-tree separates skeleton growth, which makes all random choices, from meshing, which makes none, so one seed produces every LOD ([ez-tree](https://raw.githubusercontent.com/dgreenheck/ez-tree/main/src/lib/tree.js)). Port that structure to Go with per-level arrays and add what it lacks: vertex channels, canopy normals, 32-bit indices if needed. Expose presets with a few overrides rather than its 50-plus parameters, and generate a few variants per species for instancing. Space colonization suits hero crowns later ([Runions](https://algorithmicbotany.org/papers/colonization.egwnp2007.html)). `terrain_impostor.go` already exists, so octahedral impostors ([80.lv](https://80.lv/articles/impostor-baker-for-ue4/)) should wait until tree counts demand them. Alpha to coverage needs MSAA ([Filament](https://google.github.io/filament/Materials.md.html)), so it only suits tiers with scene MSAA; alpha test with post AA is the fallback.

Grass comes after the terrain fixes, since a detail layer gives much of the perceived gain cheaply. The key idea is matching each blade root to terrain macro colour so blades dissolve into ground as they fade. A GL 3.3 adaptation of Ghost of Tsushima's approach ([GDC](https://gdcvault.com/play/1027033/), details unverified behind a paywall) uses a static tile VBO, baked textures read in the vertex shader, and index-count LOD. Clumps of about 8-15 blades are a good midpoint (estimate).

## Long soft shadows need reach and casters, not a new filter

moonBASIC already has more shadow features than the goal needs: 4 cascades, texel snap, PCSS on Ultra, shadow tint, opt-in static and dynamic cache, contact shadows and screen-space shadows (`docs/SHADOWS.md`). The gap is reach. Shadow distance defaults to about 250 units while tree reach goes to 480 (`docs/SHADOWS.md:18`, `quality.go:42-45`), and light-space Z padding is 30-100 units (`docs/SHADOWS.md:28`). A 20 m tree under a 10-degree sun has a 113 m shadow, with its top about 115 m up-light of the receiver, which exceeds that padding (estimate, assuming units are metres). So expect clipped or missing long shadows at low sun (hypothesis). Sweep caster culling along the light direction instead of using only the camera frustum, and extend the near range or use depth clamping.

Cost then falls through four moves. Interval-based selection and tight culling cost nothing visually ([Cyberpunk](https://history.siggraph.org/wp-content/uploads/2022/06/2021-Talks-Dybisz_Shadows-Optimizations-in-Cyberpunk-2077.pdf)). Far cascades render once and persist, as CRYENGINE documents ([CRYENGINE](https://www.cryengine.com/docs/static/engines/cryengine-3/categories/1114113/pages/21267738)), or update round-robin every 4-8 frames, which suits a mostly static landscape (design), but needs handling for moving casters and a moving sun. Trees draw as simple proxies in far cascades, and moonBASIC's existing cones and spheres are ready-made for this if the trunk is kept (estimate), which also avoids its per-caster cut-out path. Unigine recommends the same idea ([Unigine](https://developer.unigine.com/ch/docs/2.20/content/tutorials/vegetation/?rlang=cpp), search snippet). A coarse min-max depth reduction by fragment shader tightens cascades on 3.3, accepting 1-3 frames of latency and padding; moving partitions conflict with stable cascades, so hold them with hysteresis. Skip full SDSM histograms.

Softness comes from a kernel scaled so width stays constant in world space, which also largely hides seams ([Pettineo](https://therealmjp.github.io/posts/shadow-maps/)), plus the existing tint rather than black, and PCSS on near cascades only. Pettineo's numbers are a warning against EVSM: EVSM4 at 2048 with 4xMSAA cost about 11.5 ms more than 7x7 PCF on his PC, and about 3 ms more at 1024. Fade the last cascade properly, since a far cascade with short range can leave a hard cutoff line ([UE forum](https://forums.unrealengine.com/t/the-far-shadow-cascade-for-the-landscape-is-using-the-distancefield-shadow-distance-to-calculate-how-to-fade-out/445122)).

## Blue mountains come from sharing one atmosphere

The current sky and fog are unrelated (Code). Fog is one scalar factor, a height term evaluated only at the shaded point, user colour, and gamma-space blending, with fixed sun lobes (`shadow_shaders.go:396-411`, `linear_light.go`). The sky marches 12 single-scatter steps per fragment, with an 8-bit transmittance LUT and no multiple scattering (`atmosphere_shaders.go:86`, `atmosphere.go`). They match only if tuned by hand.

**The fix with the highest return is one function used everywhere**: per-channel Beer-Lambert optical depth integrated analytically along the view ray, using the sky's own Rayleigh and Mie coefficients, with in-scatter colour from the sky. Quilez's height-fog form is the basis ([iquilezles](https://iquilezles.org/articles/fog/), quoted via [MonoGame](https://community.monogame.net/t/solved-height-distance-based-fog-again/14371); a forum claim that it should use target height looks wrong by derivation). Using the `betaR` in `atmosphere.go`, horizontal transmittance works out as follows (estimate).

| Distance | Red | Green | Blue |
|---|---|---|---|
| 10 km | 0.94 | 0.87 | 0.72 |
| 30 km | 0.84 | 0.67 | 0.37 |
| 100 km | 0.56 | 0.26 | 0.04 |

Blue leaves the surface fastest and blue sky replaces it, which is exactly the blue-mountain effect. A 2-10 km game world gets almost none of this at physical density, so an `AerialScale` of about 5-20 is the starting estimate. As transmittance reaches zero along a level ray, surface colour converges to the sky behind it, so the horizon seam disappears (reasoning, untested). Keep the classic `Fog` command as an artist multiplier, keep Retro's stepped path, and apply the function to terrain, PBR, particles and clouds. A 3D aerial LUT is not first: its reference 4 km slices are coarse for near fog, and it adds passes. A separate analytic term handles valley fog.

**Then move the sky itself to Hillaire's LUT design**, which needs no compute at this level: the reference uses it only for the multi-scattering LUT, whose loop can run as a fragment loop ([RenderSkyRayMarching.hlsl](https://raw.githubusercontent.com/sebh/UnrealEngineSkyAtmosphere/master/Resources/RenderSkyRayMarching.hlsl)). Multiple scattering is called critical at sunset to avoid a yellowish sky, and a low-end form uses only 2 directions ([Hillaire](https://blog.selfshadow.com/publications/s2020-shading-course/hillaire/s2020_pbs_hillaire_slides.pdf)). Today's sky at 1080p is about 25M steps with sky on-screen; a 192x108 LUT at 30 steps is about 0.62M, roughly 40x fewer, and a 96x50 LUT at 8 steps about 38k (estimate). Published costs are fuzzy: slide fragments show 0.14, 0.31 and 1.03 ms with lost table layout. Secondary notes give iPhone 6s per-pass figures summing to exactly 1.03 ms ([notes](https://jojo-lyu.notion.site/s2020-Scalable-Atmospheres-in-Unreal-Engine-6cbf50aae15f4701a4c01b589f63c2c1)), so that figure is probably the mobile row. No Intel integrated figure exists. Move the transmittance LUT to 16F, since RGBA8 quantizes the small sunset values. Draw the sun disc analytically after the LUT, tinted by transmittance, and let HDR bloom make the glow. Use that same transmittance to colour the directional light, so sun, sky and world agree.

**Ambient should follow the sky.** Use L2 spherical harmonics for diffuse, as Filament recommends and Unity stores ([Filament mirror](https://www.mintlify.com/google/filament/rendering/ibl), [Unity](https://docs.unity3d.com/es//ScriptReference/RenderSettings-ambientProbe.html)), projected from the sky LUT into a 9x1 RGBA16F target with a fragment loop, refreshed every 0.25-1 s and crossfaded. A 20-minute day moves the sun 0.3 degrees per second, so faster refresh is invisible (estimate). Add an analytic ground-bounce term so undersides stop going black or sky-blue, with the same ground albedo feeding multi-scatter. For reflections, `ensureSkyCube` rebuilds 6 faces on the CPU as RGBA8 (`envcube.go`), which clips sky radiance over 1. Move to R11F_G11F_B10F or RGBA16F and update one face per frame using the probe path that already exists, following Godot's Incremental idea ([Godot](https://docs.godotengine.org/en/stable/classes/class_sky.html)). Verify separately that atmosphere changes invalidate the cube, since `skyRev` is bumped only at `skybox.go:196` in the grep performed.

**Clouds stay 2D by default.** Nubis's 2 ms was on PS4 and came after a 10x reprojection saving from about 20 ms, with 128³ and 32³ noise, a weather map, and 1-in-16 pixel updates ([Schneider](https://www.advances.realtimerendering.com/s2015/The%20Real-time%20Volumetric%20Cloudscapes%20of%20Horizon%20-%20Zero%20Dawn%20-%20ARTR.pdf)). Hillaire calls clouds the one part not reasonable on mobile. So replace per-pixel value noise (`terrain_clouds.go`) with a precomputed tileable texture and weather map, add 2-4 taps toward the sun for self-shadow, dual-lobe HG, two layers with parallax, and aerial perspective instead of a separate fade (estimate 0.2-0.5 ms). Project the weather map onto terrain as moving shadows and into ambient. That costs very little and is probably the biggest gain for tying sky to world (hypothesis). Volumetric marching at half resolution is a high-tier option at about 2 ms or more on a strong GPU.

Screen-space light shafts need no scene pass when masked from depth, at quarter resolution with 16-32 samples, faded when the sun leaves the screen ([GPU Gems 3 ch. 13](https://developer.nvidia.com/gpugems/gpugems3/part-ii-light-and-shadows/chapter-13-volumetric-light-scattering-post-process), no benchmark given). Estimate 0.3-1 ms; ship them as a tier option.

## Turquoise water is one exponential and fewer passes

Fresnel balances sky against body colour, absorption gives depth its colour, and crest scattering provides the glow. moonBASIC gets two of three wrong cheaply (Code). Absorption is `smoothstep(0.4, 6, meters)` between two colours (`water_shaders.go:306,318`). `meters` is view-axis rather than vertical depth, so shore colour shifts with view angle (`:253-263`). Fresnel is Schlick with correct F0 of 0.02, then scaled by `clamp(refl, 0.35, 1)` (`:303-304,362`), and a preset at 0.42 (`water.go:537`) caps horizon reflection at 42%, which reads as a flat band.

Replace with `T = exp(-sigma * d)` per channel, red largest, using `d = verticalDepth / max(NdotV, 0.1)`, and `refr = mix(inscatter, sceneColor, T)` (design; the Beer-Lambert basis is in [Darles et al.](https://arxiv.org/pdf/1109.6494)). **Turquoise then becomes a choice of `sigma` and `inscatter` over a pale seabed.** I found no trustworthy RGB coefficient table, so tune by eye. Gate the Fresnel change on `LinearLight` so tuned games survive, as the normal fix did. Re-orient perturbed normals so far wave backs do not sparkle. Add Sea of Thieves' crest scatter, blending subsurface colour by view, sun and a wave-peak mask, since peaks have a shorter light path ([Ang et al.](https://history.siggraph.org/wp-content/uploads/2022/09/2018-Talks-Ang_The-Technical-Art-of-Sea-of-Thieves.pdf)). That game runs from laptop integrated GPUs upward, though which settings they get is unstated.

**The performance win is larger than any wave technique.** Each water pass renders the whole scene root (`water.go:1004-1038,1067`). Three changes follow, measured against those passes (the absolute payoff is an estimate until profiled).

First, refraction does not need a scene render: GPU Gems 2 copies the back buffer, marks water in alpha, and falls back to the undistorted pixel when distortion lands outside water ([ch. 19](https://developer.nvidia.com/gpugems/gpugems2/part-ii-shading-lighting-and-shadows/chapter-19-generic-refraction-simulation)). This needs a G3N pass split (render with water hidden, copy, then draw water without clearing), and whether G3N's clear behaviour allows it is unverified. Last frame's texture is the fallback, with a one-frame lag near moving objects.

Second, the targets are the wrong shape. Square targets ignore aspect, and Ultra's 2048² is about 4.2 MP against a 2.07 MP screen (`quality.go:42-45`). Half of 1080p per axis is about half the pixels of today's High (estimate). Ryzom defaults to half resolution because bump distortion hides it, sizes the target once and renders a sub-region to avoid reallocation, skips shadow generation in the reflection pass, and biases the clip plane ([Ryzom wiki](https://github.com/ryzom/ryzomcore/wiki/water_planar_reflection), project wiki).

Third, add a reflection render list: distance cap, no scatter or small props, lowest terrain LOD, a script flag for landmarks, with sky beyond the cap blended by distance rather than by colour, since a magnitude-weighted blend wrongly erased dark reflections in one build ([Cinevva](https://app.cinevva.com/blog/2026-05-12-open-world-browser-part-26-water)). Half-rate reflection comes last, if at all: a forum user reports visible lag ([Unity forum](https://discussions.unity.com/t/best-usage-for-realtime-reflection-planes/814717)), and I found no source testing it on water.

**The Low tier has the largest gap.** `autoTier` sends Intel HD to Low (`quality.go:68-69`), where `reflectCol` is one constant colour and no depth exists for surf (`water_shaders.go:330,400`). A single-pass Low needs no FBOs: a three-colour gradient by reflection Y or a low-mip sky cube, baked depth from the terrain, alpha `mix(1 - T, 1, fresnel)`, two normal scrolls, a sun lobe, and baked shore. GPU Gems 1 is the template ([ch. 1](https://developer.nvidia.com/gpugems/gpugems/part-i-natural-effects/chapter-1-effective-water-simulation-physical-models)), and Ryzom and BeamNG fall back the same way. Compile a Low variant with `#define`s rather than uniform branches. Godot's note that `if` branches raise VGPR use supports that choice.

**Detail then replaces tile repetition.** The tile runs a separable inverse DFT looping all 64 samples per fragment (`water_fft_gpu.go`). Radix-2 is 49k loop iterations against 524k at N=64, 229k against 4.2M at 128, and 1.05M against 33.6M at 256 (estimate). At 64 the real gap is below 10x, because FFT uses 12 passes against 2; test it. Fragment-only FFT is established ([glsl-rfft](https://www.npmjs.com/package/glsl-rfft), [fft-ocean](https://github.com/jbouny/fft-ocean)). Carry height, horizontal displacement and slopes straight from the spectrum, since Tessendorf's Jacobian gives a foam signal ([Tessendorf](https://jtessen.people.clemson.edu/reports/papers_files/coursenotes2002.pdf)). Use 2-3 cascades at unrelated sizes with bands masked to avoid doubled energy; my suggested 250, 37 and 5.3 m are unverified. For Low and Medium, a looping tile baked at load into a texture array is cheaper: 256² RG8 at 64 frames is 8.4 MB before mips and needs no GPU simulation (estimate). Crest's rule of matching wavelengths to LOD ([Crest](https://crest.readthedocs.io/en/4.9/user/technical-information.html)) and GPU Gems 1's edge-length fade are worth copying; its rings are not needed yet. Public detail on Assassin's Creed water is too thin to cite.

**Foam should remember.** Crest foam today is an instantaneous function of absolute height (`water_shaders.go:392-397`), so every tall wave gets it. One small R8 ping-pong with `foam = max(source, prev * decay)` gives lingering foam, as Sea of Thieves' feedback and blur and the Habr ocean's history blending both show ([Habr](https://habr.com/en/articles/451604)). Bake a distance-to-shore map from terrain at water creation and sample it with undisplaced XZ, or shallows swim as they did in Crest ([issue 96](https://github.com/wave-harmonic/crest/issues/96)). Moving surf bands then march up its gradient, phase-varied so they do not ring the coast evenly, an idea Horizon's variation texture supports ([Malan](https://advances.realtimerendering.com/s2022/SIGGRAPH2022-Advances-Water-Malan.pdf)). Flow maps cost 5 samples ([Catlike Coding](https://catlikecoding.com/unity/tutorials/flow/texture-distortion/)), so keep them for rivers.

## Post-processing gains most from putting passes in the right order

moonBASIC's `fxaa()` averages a pixel with four neighbours above a contrast threshold, with no edge direction, search or sub-pixel logic, and it runs on HDR input at line 239 before `tonemap()` at line 272 (Code, `postfx_shaders.go`). That is a gated blur in the place FXAA's whitepaper warns against: averaging 0.0 and 16.0 gives 8.0, which may still tonemap to 1.0, so bright edges get no visible blend ([whitepaper](https://developer.download.nvidia.com/assets/gamedev/files/sdk/11/FXAA_WhitePaper.pdf)). Sky silhouettes against dark trees are exactly that case. FSR also runs after the whole pass (`fsr.go`), so grain, retro palette and rain get upscaled and sharpened, contrary to AMD's guidance that noise-adding passes follow FSR ([AMD](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-spatial/)).

The recommended order on the forward path: opaque with sky; depth and colour copy; transparent and water; NaN cleanup; optional TAA and SSR; DoF then motion blur; bloom mixed in HDR; exposure, tonemap, encode; grade and LUT; outlines; SMAA or FXAA; FSR EASU and RCAS or plain sharpen; vignette and chromatic aberration; retro palette in display pixels; grain and 8-bit dither; UI. No authority gives this exact order. HDRP's documented sequence has SMAA early, which conflicts with SMAA's own requirement for gamma-corrected input, so do not copy HDRP without checking its encoding ([HDRP](https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@16.0/manual/rendering-excecution-order.html), [SMAA.hlsl](https://raw.githubusercontent.com/iryoku/smaa/master/SMAA.hlsl)). Retro modes should skip FSR, and `dynActive` already excludes low-resolution retro (`dynres.go:128`).

| AA method | Published cost | Hardware | Source |
|---|---|---|---|
| FXAA preset 2 | Under 1 ms | GTX 480, 1920x1200 | [FXAA whitepaper](https://developer.download.nvidia.com/assets/gamedev/files/sdk/11/FXAA_WhitePaper.pdf) |
| SMAA 1x | 1.02 ms | GTX 470, 1080p | [SMAA paper](https://www.iryoku.com/smaa/downloads/SMAA-Enhanced-Subpixel-Morphological-Antialiasing.pdf) |
| SMAA 4x | 2.34 ms (figure caption says 2.6) | GTX 470, 1080p | same |
| MSAA 8x | 5.4-7.7 ms, up to 126 MB in forward | GTX 470 | same |

These come from different setups on 2010-2011 GPUs, so compare them loosely. SMAA is MIT-style, has a `SMAA_GLSL_3` target, and needs two targets, two small textures and three passes ([SMAA.hlsl](https://raw.githubusercontent.com/iryoku/smaa/master/SMAA.hlsl)). Long straight low-poly edges suit morphological AA, so SMAA 1x at medium or high is the upgrade, with FXAA 3.11 as the cheap tier. Move outlines before AA so they smooth. FXAA and SMAA read dither as edges, so retro dither follows AA.

**Bloom** already has five levels, but it uses a threshold-style extract. LearnOpenGL gives a `#version 330 core` Jimenez-style chain of 13-tap downsample, 9-tap tent upsample, Karis average on the first mip, in `R11F_G11F_B10F`, mixed near 0.04 ([LearnOpenGL](https://learnopengl.com/Guest-Articles/2022/Phys.-Based-Bloom)). ARM's dual filter is the low-tier option: fastest in its Mali test at 7% of the bandwidth of the linear-sampling filter ([Bjørge](https://community.arm.com/cfs-file/__key/communityserver-blogs-components-weblogfiles/00-00-00-20-66/siggraph2015_2D00_mmg_2D00_marius_2D00_notes.pdf)).

**Tone mapping has no declared winner, so offer it per profile.** Narkowicz himself calls his fit "luminance only" and says it oversaturates brights ([Narkowicz](https://knarkowicz.wordpress.com/2016/01/06/aces-filmic-tone-mapping-curve/)). Hill's fit has working-space matrices ([three.js](https://raw.githubusercontent.com/mrdoob/three.js/dev/src/renderers/shaders/ShaderChunk/tonemapping_pars_fragment.glsl.js)). Khronos PBR Neutral keeps base colours exact from 0.08 to 0.8 ([Khronos](https://github.com/KhronosGroup/ToneMapping/blob/main/PBR_Neutral/README.md)), though a Blender developer says it is not generally better and reports negative shadows with saturated lights ([Blender](https://devtalk.blender.org/t/adding-pbr-neutral-tone-mapper/33602?page=2)). AgX is desaturated out of the box ([Bevy](https://doc.qu1x.dev/bevy_trackball/bevy/core_pipeline/tonemapping/enum.Tonemapping.html)). For this rich landscape, test Neutral plus a small saturation and split-tone grade on Stylized, and Hill or AgX with a look on Advanced, on a sunlit tree, a shaded tree, a sunset and an emissive. Switching from Narkowicz changes brightness by about 1.67x, so re-tune exposure. The actual look lives in the LDR grade: cool lifted shadows, warm highlights, a slight midtone saturation lift, through a 32³ LUT that can blend through the day. Firewatch got most of its colour from lighting, fog and grading, with mostly grey rock diffuse ([Campo Santo](https://blog.camposanto.com/post/102893584324/i-asked-twitter-if-anyone-had-questions-about-the), search excerpt). That is the best single precedent for the requested look. **Add 8-bit output dither early**, because gradient skies band and it costs one small read.

## One material record can serve three profiles

The Classic, Stylized and Advanced design is sound if profiles only change defaults. Filament shows the precedent: a shared parameter vocabulary, a selectable shading model, and `customSurfaceShading` swapping the per-light function while the rest of the lit pipeline remains ([Filament](https://google.github.io/filament/main/materials.html)). Style must be per material, because forward picks a shader per draw at no extra cost and whole-frame effects are the only true conflict. The notes differ slightly on whether a profile selects "only a light function, ambient, shadow defaults, tone map and grade" or also a material selector. I resolve that in favour of a `shading` field per material (`unlit`, `ramp`, `toon`, `retro`, `pbr`) with the profile as the default for it, because a secondary write-up says Breath of the Wild mixes shading by material ([Set Side B](https://setsideb.com/?p=3303), not a Nintendo source) and Godot's note that switching renderers needs manual tweaks shows drift is a real cost ([Godot](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)).

Use glTF metallic-roughness names exactly so importers map directly, then a small stylize block that `pbr` and `unlit` ignore: ramp, shadow tint, rim, specular steps, flat shade, outline mask, dither fade. A ramp must multiply shadow visibility, or shadows ignore it. Never change a parameter's meaning between profiles. Generate programs from `#define`s, compile lazily on demand, cache by key, and keep style differences inside one surface-shading include. For cheap object gains, geometric specular AA is about 4 lines using Filament's variance 0.15 and threshold 0.2 ([Filament](https://google.github.io/filament/Materials.md.html)); the exact shader is from memory, so check it against [Tokuyoshi and Kaplanyan](https://www.jcgt.org/published/0010/02/02/paper-lowres.pdf). Multi-scattering compensation mainly helps rough metals, so it will do little for this look. A future material editor should copy MaterialX's idea of typed nodes compiled to generated GLSL, targeting `#version 330 core`, and not the library. Keep any shader-chunk hooks few and named, since three.js's move from string patching to node materials suggests chunk names become a compatibility burden ([Material docs](https://threejs.org/docs/pages/Material.html)).

## Bake assets at build time and label everything for debugging

**Textures should be BC by `moon build`.** Basis Universal's value is one file for many GPUs, which the desktop does not need, because BC covers every vendor and Intel Macs ([KTX guide](https://raw.githubusercontent.com/KhronosGroup/3D-Formats-Guidelines/main/KTXDeveloperGuideWebGL.md)). Transcode offline, ship KTX2 with BC payloads, and read Zstd through `klauspost/compress`, already in `go.mod`. At runtime: BC7 if BPTC is exposed, else BC3/BC1, BC4/BC5 for one- and two-channel data, BC5 for normals. **Never pick ETC2 or ASTC because the extension string appears**, since desktop ETC is mostly decompressed in software ([KTX guide](https://github.com/KhronosGroup/3D-Formats-Guidelines/blob/main/KTXDeveloperGuide.md)) and sources conflict on Intel ASTC, with hardware reported removed at Gen12.5 ([Phoronix](https://www.phoronix.com/news/Intel-Gen12.5-No-ASTC)). Which BC formats Apple's GL exposes needs a hardware test. I found no pure-Go Basis transcoder; if third-party `.ktx2` must load, choose between cgo on one C++ file and wazero plus a WASM transcoder only after a prototype.

**HDR and IBL fit fragment shaders.** Write a small in-tree Radiance decoder, since `Opioid/rgbe` has no visible licence ([rgbe](https://github.com/Opioid/rgbe)), and pin `mokiat/goexr` for ZIP and uncompressed EXR, rejecting others with a clear re-save message ([goexr](https://github.com/mokiat/goexr)). LearnOpenGL's split-sum path (128-per-face prefilter with 5 mips, 512² BRDF LUT, seamless cubes) needs no compute ([LearnOpenGL](https://learnopengl.com/PBR/IBL/Specular-IBL)). Cache results at build; check `envcube.go` and `pbr.go` first, because parts already exist.

**Treat glTF's Testing list as the regression suite.** Validate first so asset errors are not chased as loader bugs ([Validator](https://github.com/KhronosGroup/glTF-Validator)), load the Testing list ([list](https://raw.githubusercontent.com/KhronosGroup/glTF-Sample-Assets/main/Models/Models-testing.md)), and compare against the Sample Renderer ([renderer](https://github.com/KhronosGroup/glTF-Sample-Renderer)), since same-machine diffs prove only "unchanged". Licences vary per model, so fetch rather than vendor. Add `KHR_texture_transform`, `KHR_materials_unlit`, `KHR_materials_emissive_strength`, `KHR_mesh_quantization` and WebP first, then meshopt and `EXT_mesh_gpu_instancing`. Reject files whose `extensionsRequired` you lack. `moon snapshot` already exists, but it was only ever drawn on one GPU, so extending references to a second vendor is cheap, high-value testing.

**Debugging needs labels more than tools.** RenderDoc captures core 3.2-4.6 on Windows and Linux but not macOS, requires frame GL from one thread, and shader debugging needs compute and SSBO extensions, so a pure 3.3 driver path may lose it ([RenderDoc](https://renderdoc.org/docs/behind_scenes/opengl_support.html)). The go-gl binding already exposes the functions, but pointers can be nil, and `internal/` currently uses none of them. Add a `MOON_GL_DEBUG` flag that sets a debug context, because without one the GL may emit nothing, and use `DEBUG_OUTPUT_SYNCHRONOUS` so callbacks stay on the render thread in Go ([KHR_debug](https://registry.khronos.org/OpenGL/extensions/KHR/KHR_debug.txt)). Then add `PushDebugGroup` per pass, using the same names as the profiler, and `ObjectLabel` with asset paths ([annotation](https://renderdoc.org/docs/how/how_annotate_capture.html)). Standardize on timestamp pairs, since nested `TIME_ELAPSED` is illegal and `particles_gpu.go` uses it ([ARB_timer_query](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_timer_query.txt)). Read results only when available. Check `QUERY_COUNTER_BITS` at startup. NVIDIA has Nsight ([docs](https://docs.nvidia.com/nsight-graphics/UserGuide/appendix.html)), AMD's RGP "will NOT work" with OpenGL ([RGP](https://gpuopen.com/manuals/rgp_manual/)), and on macOS the engine's own overlay is what remains. Consolidate the five `gl.Init()` sites while here.

## As powerful as OGRE means extensibility, not more features

**OGRE 1.x is the fair benchmark, and Ogre-Next is not.** OGRE, now numbered 14.x with v14.6.3 released on 2026-11-01, is an active MIT-licensed C++ renderer ([releases](https://api.github.com/repos/OGRECave/ogre/releases), [README](https://github.com/OGRECave/ogre/blob/master/README.md)). Its GL3Plus back end asserts the same OpenGL 3.3 floor and gates tessellation, program binaries and compute at runtime ([OgreGL3PlusRenderSystem.cpp](https://github.com/OGRECave/ogre/blob/master/RenderSystems/GL3Plus/src/OgreGL3PlusRenderSystem.cpp)), so moonBASIC's GL policy needs no change to match it. The project itself calls the two lines "sister projects" that do not share an API ([comparison](https://www.ogre3d.org/about/what-version-to-choose)). HLMS belongs to Ogre-Next: of 3,131 paths in OGRE's tree, the only "hlms" filename is a thumbnail ([git tree](https://api.github.com/repos/OGRECave/ogre/git/trees/master?recursive=1)), and OGRE's shader generation is RTSS ([RTSS](https://ogrecave.github.io/ogre/api/latest/rtss.html)). I would state the goal as "as capable as OGRE 1.x on its GL3Plus back end, plus a full game layer".

This is a feature comparison only, because no benchmark compares the two engines. OGRE facts below come from its manuals and repository. moonBASIC facts come from its docs and from searches of registered command names, which can miss internals.

Being ahead on that list says nothing about how good the result looks. The notes disagree here: the OGRE note calls moonBASIC's sky "Bruneton-style", while the code keeps only a transmittance LUT and marches single scattering per pixel (`atmosphere.go`, `atmosphere_shaders.go:86`). I trust the code, and the earlier sections show that moonBASIC's sky, water and terrain still have real faults. OGRE's many samples, such as `Hair`, `Smoke` and `GaussianSplatting`, are shader demos on top of the engine, so counting them as engine features would overstate the gap.

**Five designs are worth copying, none wholesale.** The compositor comes first: a minimum version is `CreateRenderTexture`, `CameraToTexture` and `AddPostPass shader$, scale#, inputs$`, plus a small hot-reloadable text format, with built-in bloom and tonemap kept as named passes ([Compositor Scripts](https://ogrecave.github.io/ogre/api/latest/_compositor-_scripts.html)). Row 9's pass split is the natural base, and it would let users build DoF, motion blur and shafts themselves. Second, OGRE's resource states separate prepared data from GPU-loaded data, and with default threading its workers never touch the render system ([background queue](https://github.com/OGRECave/ogre/blob/master/OgreMain/include/OgreResourceBackgroundQueue.h)). That matches moonBASIC's existing rule, so `LoadGroup`, `LoadProgress` and `GroupLoaded` fit Blitz style. Check `stream.go` first, because terrain streaming may already do part of this. Third, OGRE's microcode cache ([GpuProgramManager](https://github.com/OGRECave/ogre/blob/master/OgreMain/include/OgreGpuProgramManager.h)) supports row 14, gated like OGRE on 4.1 or the ARB extension. Fourth, named queues ([OgreRenderQueue.h](https://github.com/OGRECave/ogre/blob/master/OgreMain/include/OgreRenderQueue.h)) cost little and become the layer field of row 28's sort key, but decide up front how they interact with batching. Fifth, copy the rule behind ordered techniques ([Material Scripts](https://ogrecave.github.io/ogre/api/latest/_material-_scripts.html)) without their multi-pass state: a water material could offer "full", "no-refraction" and "unlit" variants, chosen by tier and distance, which turns `tierSettings` from a global switch into per-material decisions. A cheap reflection scheme would help Medium and above, since Low has no reflection pass today (`quality.go:42`). For shader variants, Ogre-Next's hash-keyed lookup, where the same property set means the same shader, is the simplest scheme ([HLMS](https://ogrecave.github.io/ogre-next/api/latest/hlms.html)), and it matches what row 8 already proposes.

**Forward+ is where the benchmark and the target look pull apart.** The OGRE note lists it as the one large gap and likely worth doing through a UBO or texture buffer. I rank it last anyway. The requested landscape has one sun, Godot's cost model says clustering raises base cost on weak GPUs, and fixed per-object light slots come first. I could not establish OGRE's GL requirement or light limits for it, so even OGRE's own 3.3 support is unconfirmed. If "as powerful as OGRE" must mean many-light scenes, row 34 moves up, and its first task is timing on an HD 520-class GPU.

**Embedding OGRE is not sensible, and size is not the reason.** Python wheels of 10-26 MB compressed ([PyPI](https://pypi.org/pypi/ogre-python/json)) are an imperfect size proxy, and small next to the current 80 MB `moon.exe`. The obstacle is that two scene graphs cannot share a GL pipeline cleanly, so adoption means replacing G3N and porting most of what gives moonBASIC its look (judgement). SWIG supports Go ([SWIG](https://swig.org/Doc4.4/Go.html)), but OGRE's official bindings are C#, Java and Python, and the Go wrappers are over a decade stale. The only gains unreachable on GL 3.3 are extra back ends and mobile or web targets. Treat OGRE as one candidate in any future renderer replacement, tested as a spike through a narrow hand-written C layer.

## What this research could not establish

Several gaps limit confidence. No moonBASIC measurement exists on Intel, NVIDIA or Apple hardware, and no public benchmark of any terrain, water, cloud or AA technique on Intel HD class GPUs was found, so all Low-tier budgets are designs. Driver behaviour for RG32F targets on old Intel, timer reliability on Mesa, Intel and Mac GL, and whether Godot's and Unity's omission of GL from dynamic resolution reflects real timing faults are all open. Karis's split-sum paper, Hillaire's full paper, Ladavac's post, the Tsushima grass talk, and Bend's contact-shadow details were not read. First-party detail on Fortnite, Wind Waker, Sable, Tunic, Assassin's Creed water and Legion is absent, so this report does not attribute methods to them. Formulas marked as starting values need tuning, and shader sketches in the notes are untested in moonBASIC. For OGRE, the terrain manual page could not be fetched, ParticleFX behaviour and 1.x anisotropy support were not checked, and OGRE was never built through cgo. Rows 2, 7, 8 and 14 rest on code reading and should each get their decisive test before significant work begins.

## Conclusion

The research changes what "upgrading the renderer" means here. The expected shopping list of clustered lights, Forward+, Vulkan, volumetrics and occlusion culling turns out to be mostly wrong for this engine and this target. moonBASIC's own city test already argued against occlusion culling, that same test's draw count already sits below one capture of a shipping 2016 shooter, and its GL 3.3 path already passes Godot's. The real leverage is that several current subsystems were never connected: fog does not read the sky, water colour does not model absorption, AA does not see tonemapped values, the resolution controller does not act on GPU time, and foliage has no shaded-side model. Connecting them costs little at runtime, which is why the requested look and the requested smoothness stop competing. The OGRE benchmark points the same way from another angle: the honest gap is not a missing renderer but a pipeline that developers cannot reach into, and render targets, a post chain and a few selection rules close most of it on the current back end.

One implication is easy to miss. The cheapest way to make games run on more computers is to give Low a designed look rather than a stripped one, because Low currently means constant-colour water, a gamma path and a different picture from Medium. A 2016 laptop running baked terrain masks, sky-coloured haze, tinted soft shadows and one-pass turquoise water would show the same landscape as a new GPU at lower resolution. That is a testable goal, and the first step is buying or borrowing an HD 520-class laptop and a Mac, then running the pass table of row 1 on them.
